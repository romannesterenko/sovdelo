# Этап 26 — метки Android/Linux

Технический интерфейс остаётся прототипом. Отдельный этап переработки зафиксирован
в docs/client-ux-plan.md; он обязателен до повседневного использования и публикации.

На экране аккаунта кнопка «Метки»: каталог, цвет и создание метки. Каталог доступен
без сети после успешного чтения; новая метка сохраняется локально и отправляется позже.
В редакторе задачи можно выбрать/снять до 20 меток, на карточке отображаются цветные
бейджи. Новые метки создаются в каталоге отдельно от редактора: отмена редактирования
задачи не отменяет уже созданную запись каталога. Название 1–40 символов, шесть цветов.
Переименование/удаление самих меток и фильтры пока не реализуются.

## Сервер

GET /api/v1/labels?after_id=0[&through_id=N]: каталог текущего владельца, до 100 записей,
meta.through_id/after_id/has_more. Read-токен достаточен. DTO: id, name, color.
POST /api/v1/sync/operations:
```json
{"operation_uuid":"UUID","kind":"label","label_name":"Работа","label_color":"red"}
```
Нужен write. Ответ 201: data.operation_uuid, data.label. Повтор того же UUID/тела
возвращает прежний результат, другое тело — 409. Имя уникально в аккаунте. Если оно
уже существует, используется существующая метка с ЕЁ цветом, без изменения серверной
записи. Это предотвращает дубликаты при создании с разных устройств. Другая раскладка/
регистр имени считаются другим именем по существующим правилам PostgreSQL.

kind=edit дополнен fields.label_ids: полный список ID, до 20, distinct, [] снимает все.
Доступность/владелец меток проверяются внутри транзакции после поиска подтверждения,
до изменения полей. Нельзя назначить чужую метку или частично записать title при ошибке.
Изменение набора меток увеличивает версию задачи; смена набора через веб теперь тоже
увеличивает version. Повтор того же набора в вебе не меняет версию. Поэтому офлайн-
назначение после чужой правки получает 409. Прочие поля и очереди не перезаписываются.
Новая миграция PostgreSQL не нужна.

## SQLite v5 и зависимости операций

labels_json хранит ссылки на локальные записи account_labels. Серверная запись имеет
ключ server-label-ID; офлайн-создание — временный UUID. При подтверждении/обнаружении
имени в полном каталоге UUID заменяется на серверный ключ в локальных задачах и
локальных намерениях очереди. Уже замороженное HTTP-тело при этом не изменяется.
При необходимости несколько ссылок на один серверный ID объединяются.

Worker сначала читает задачи, проекты и весь каталог меток, затем отправляет новые
метки, после — задачи и комментарии. Тело назначения с numeric label_ids фиксируется
только после разрешения локальных ссылок. Если зависимая метка блокирована, правка
задачи также останавливается; другие задачи продолжают отправляться. Успешное
подтверждение метки снимает только эту специальную блокировку зависимости, не конфликт
версии. Каталог позволяет повторить блокированное создание метки. При конфликте задачи
по-прежнему можно явно принять сайт и повторить выбор меток; комментарии сохраняются.

Потеря ответа создания: полный каталог узнаёт уже существующее имя, принимает его
серверный ID/цвет и не создаёт ещё одну метку. Назначение продолжает отправляться
с собственной проверкой версии задачи. Если имя уже было создано на другом устройстве
с другим цветом, победивший цвет виден после обновления каталога.

Миграция v4→v5 создаёт account_labels и labels_json из прежних DTO remote_json.
Ранние прямые миграции v1/v2/v3 также поддерживаются. Точные prepared-тела, UUID,
комментарии, чек-листы и поля задач сохраняются. Общий счётчик включает новые метки.
Не удалять локальную базу; повторный вход с прежним write-токеном не нужен.
Каталоги разных аккаунтов не смешиваются. Изменения остаются пользовательскими
действиями; фоновой синхронизации пока нет.

## Приёмка

1. Установить, выполнить backend/Flutter тесты, commit/push, дождаться зелёного Actions.
2. Открыть аккаунт → «Метки», создать метку с цветом. В редакторе задачи выбрать её,
   сохранить и проверить бейджи/сайт. Снять все метки, проверить сайт.
3. Без интернета создать другую метку и назначить её задаче. Перезапустить приложение:
   каталог, выбор и очередь остаются. Включить сеть, синхронизировать: одна метка,
   корректное назначение, очередь пуста.
4. Повторить для задачи, ещё не отправленной на сервер.
5. Создать на сайте метку с тем же именем до отправки офлайн-метки: должна использоваться
   серверная запись и её цвет, без дубля.
6. Сменить метки на сайте, пока локальная правка ждёт отправки: получить конфликт версии,
   не автоматическую перезапись. Принятие сайта заменяет и набор меток.

Добавлены 4 Laravel- и 7 Flutter-проверок создания/повтора, назначения/снятия,
веб-версии/владельца, перезапуска, потери ответа, разрешения ссылок, зависимостей,
валидации и миграции v4. PHP/Flutter в среде подготовки отсутствуют: тесты запускаются
локально. Установщик и SQL нового каталога проверяются отдельно.
