# Этап 25 — история и офлайн-комментарии

В карточке аккаунта доступна кнопка «Комментарии (N)». N — серверный счётчик по
последнему обновлению; рядом отдельно показываются ожидающие/отклонённые локальные
комментарии, чтобы не складывать неизвестное подтверждение дважды.
Диалог показывает автора, время устройства (из UTC), текст и состояние.
История доступна офлайн после её первой успешной загрузки; при отсутствии кэша
сообщение «нет сохранённой истории» не означает отсутствие комментариев на сайте.

Новый текст сохраняется в SQLite при нажатии «Сохранить и отправить», после чего
поле ввода очищается и выполняется попытка синхронизации. Набранный, но не сохранённый
текст при закрытии диалога не сохраняется. Предел 1–10000 символов после trim.
Новые сообщения к офлайн-задаче ждут подтверждения её создания.
Редактирование/удаление опубликованных комментариев с телефона пока не реализовано;
правки/удаления на сайте отражаются при полном обновлении истории.

## API и PostgreSQL

Миграция добавляет nullable client_uuid в task_comments и уникальность user_id+client_uuid.
Старые и веб-комментарии продолжают работать с null. Остальные таблицы не меняются.
Деплой GitHub Actions выполняет миграцию обычным процессом после резервной копии.

GET /api/v1/tasks/{id}/comments?after_id=0[&through_id=N]: до 50 записей по ID,
meta.through_id/after_id/has_more. Проверка владельца задачи обязательна, read-токен
достаточен. DTO: id, uuid (nullable), task_id, body, author, created_at, updated_at.
Первый ответ ограничивает верхний ID обхода; изменения уже пройденных сообщений
могут отразиться лишь при следующем полном чтении. Это не атомарный снимок во времени.

POST /api/v1/sync/operations, write-токен:
```json
{"operation_uuid":"UUID","kind":"comment","task_id":123,"comment_body":"Текст"}
```
expected_version не передаётся: добавление комментария не перезаписывает поля задачи.
Комментарий и api_requests-результат сохраняются в одной транзакции под блокировкой
пользователя. Повтор UUID с тем же содержимым возвращает исходный ответ 201, другое
содержимое — 409. data содержит operation_uuid, comment и task. Версия задачи от
самого комментария не меняется, но comments_count в свежем DTO увеличивается.
client_uuid комментария равен UUID операции, что позволяет узнать запись при чтении,
если ответ на создание потерялся. Публикация разрешена в архивную задачу, как в вебе;
задача в корзине для новой публикации недоступна. Повтор уже успешной операции
возвращает результат даже после перемещения задачи в корзину.

## SQLite v4 и очереди

Новая account_comments хранит опубликованный кэш и локальные сообщения. Отдельная
очередь комментариев (state pending/blocked) не зависит от конфликтов полей задачи.
Точное тело фиксируется в request_json до HTTP, повтор использует тот же UUID и тело.
Подтверждение помечает запись sent, не заменяя локальные поля/базовую версию задачи.
При 401/403/429/5xx/таймауте очередь остаётся. При 404/409/422 сообщение блокируется:
в диалоге можно повторить после исправления причины или явно убрать его с устройства.
Убрать опубликованный текст с сайта этим действием нельзя.

История применяется только после чтения всех страниц. Заменяются лишь sent-записи
этой задачи; неподтверждённые сохраняются. Совпадающий client_uuid подтверждает
локальную запись без дубля. Это также отражает последующее редактирование/удаление
на сайте. После отправки комментариев worker обновляет затронутые истории.
При обычном обновлении аккаунта без отправки чужие истории не скачиваются целиком;
актуализация конкретной истории — при открытии/обновлении диалога.

Общий счётчик очереди включает комментарии. Задача с неподтверждённым комментарием
остаётся видна даже после архива/удаления на сайте. «Принять сайт» в конфликте полей
сохраняет комментарии. Явное подтверждение удаления ВСЕХ локальных изменений
недоступной задачи очищает также её неподтверждённые комментарии.
Миграция v3→v4 не меняет prepared-тела прежних операций полей/чек-листов.
Базы разных аккаунтов остаются отдельными; токен/пароль в таблицу не записываются.
На 401 внутри диалога текст очереди остаётся доступен: закрыть диалог, выйти/войти
в аккаунт и повторить синхронизацию. Опубликованные комментарии могут отсутствовать
офлайн до первого открытия истории — это кэш по требованию, не полная копия аккаунта.

Синхронизация по-прежнему выполняется при действиях и вручную, не в фоне.
При отсутствии сети возможна задержка таймаута до 25 секунд; после восстановления
сети нажать «Обновить и отправить очередь» или «Синхронизировать» на экране аккаунта.

## Приёмка

1. Установить, выполнить локальную PostgreSQL-миграцию и тесты, commit/push.
   Дождаться зелёного Actions с миграцией production, затем запускать клиент.
2. Открыть существующую задачу → «Комментарии». Сверить автора/текст с сайтом.
3. Добавить сообщение, проверить появление на сайте ровно один раз.
4. Отключить сеть, сохранить сообщение, полностью закрыть/открыть приложение:
   локальная история и ожидающее сообщение сохраняются.
5. Включить сеть, обновить: сообщение появляется на сайте и меняет состояние на sent.
6. Повторить для задачи, созданной офлайн до её первой отправки.
7. Изменить/удалить комментарий на сайте, обновить диалог: кэш отражает изменения.
8. Проверить, что конфликт описания/чек-листа не удаляет ожидающие сообщения.
9. Проверить чужой аккаунт: его история и очередь не смешиваются с прежними.

Добавлены 4 Laravel- и 9 Flutter-проверок: повтор/потеря ответа, курсор, права,
валидация, архив/корзина, кэш, ожидание create, полный/оборванный обход,
конфликт полей, миграция и ошибка SQLite. SDK PHP/Flutter здесь отсутствуют:
тесты подготовлены, но запускаются на машине разработчика. Установщик и SQL
создания локальной таблицы проверяются отдельно.
