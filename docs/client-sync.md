# Этап 22 — синхронизация создания и статуса задач

Входит: отдельная SQLite на аккаунт production, офлайн-копия задач,
создание личной задачи без проекта, изменение todo/doing/done, долговечная очередь,
идемпотентные подтверждения на сервере, явная остановка при конфликте версии.
Локальный прототип probe.sqlite3/outbox остаётся отдельно и не импортируется.

## API

GET /api/v1/me дополнен access=read|write.
GET /api/v1/tasks/{id} дополнен active с учётом архива проекта/задачи и корзины.

GET /api/v1/sync/tasks?after_id=0[&through_id=N]: до 20 записей по возрастающему id,
включая архив и корзину. Первый ответ фиксирует верхний id обхода; следующие запросы
передают through_id. meta: through_id, after_id, has_more. Нет сортировки по позиции
доски, которая могла бы сдвинуть страницы во время переноса. Чужие записи исключены.
Полный обход загружается и применяется к SQLite только после получения всех страниц.
Это повторяемое чтение с eventual consistency, НЕ атомарный снимок во времени:
правки уже пройденных записей видны при следующем полном обновлении.
При отсутствии записи в полном обходе чистая локальная копия скрывается;
очередь изменённой задачи сохраняется до ответа на её операцию/решения пользователя.

POST /api/v1/sync/operations — нужен write-токен.

Создание:
```json
{"operation_uuid":"UUID","kind":"create","title":"Задача"}
```
UUID создания становится серверным uuid задачи и локальным local_id. Это позволяет
узнать задачу в чтении, если создание уже выполнено, а ответ потерян.

Статус:
```json
{"operation_uuid":"НОВЫЙ-UUID","kind":"status","task_id":123,"expected_version":2,"status":"done"}
```
Ответ data: {operation_uuid, task: DTO с active}. Создание 201, статус 200.
Изменение и запись результата в api_requests находятся в одной PostgreSQL-транзакции
под существующей блокировкой строки пользователя. Повтор UUID с тем же валидированным
содержимым возвращает исходный результат даже после последующих правок задачи.
Другое содержимое с тем же UUID — 409. Результаты операций не удаляются по таймеру.
Общая уникальность UUID с прежними create-операциями API сохранена.
Конфликт expected_version — 409 без подтверждения, изменение чужого объекта — 404,
архив — 422. Закрытие таймера при done использует существующий TaskOrder.
Новая серверная миграция не нужна: используется api_requests из патча 18.

## Клиент

production-account-{user_id}-v1.sqlite3, фиксированный production origin.
Токен и последний подтверждённый профиль сохраняются вместе в системном хранилище.
Профиль нужен для открытия правильной SQLite без сети; токен по-прежнему проверяется
сервером при каждом запросе. После 401 интерфейс аккаунта закрывается, файл очереди
сохраняется. При повторном входе в тот же аккаунт очередь восстанавливается.
Выход не удаляет локальные задачи аккаунта; другие аккаунты используют другой файл.
Хранилище совместимо с raw-токеном патча 21.

Первый токен патча 21 read: выйти и войти повторно, чтобы получить write и отозвать
прежний токен. Пока токен read, редактирование выключено. Автоматического повышения
прав нет. Пароль по-прежнему не сохраняется.

Локальное изменение и операция очереди записываются одной транзакцией.
Операция содержит снимок намерения; точное тело с ожидаемой серверной версией
фиксируется в SQLite до HTTP. Повтор использует тот же UUID и тело, включая после
перезапуска. Успешный ответ и удаление операции применяются одной локальной транзакцией.
Последующие офлайн-правки той же задачи сохраняются, а их expected_version берётся
из подтверждения предыдущей операции. Pull не заменяет локальный желаемый статус
и базовую версию, пока есть очередь. Перед отправкой выполняется полный pull:
это также проверяет наличие новой версии API до первой записи.

При 401/403/429, 5xx, таймауте и сетевой ошибке очередь остаётся. При 404/409/422
операция блокируется вместе с последующими операциями той же задачи; другие задачи
могут отправляться. «Разобрать конфликт» показывает локальный/серверный статус.
«Принять сайт» после явного подтверждения удаляет ожидающие изменения только этой
задачи и принимает прочитанную версию. Для безвозвратно недоступной серверной задачи
предлагается отдельно подтвердить удаление её локальных изменений.
Принудительная перезапись серверной версии не реализована.

Синхронизация запускается при открытии экрана, после изменения и по кнопке.
Фоновый worker, периодический опрос и автоматическое событие восстановления сети
пока не подключены. После восстановления сети нажать «Синхронизировать».
Немедленная локальная запись не зависит от сети; ожидание сетевого таймаута до
25 секунд может временно блокировать элементы экрана, затем локальный список доступен.

Проекты остались доступны для онлайн-просмотра отдельной кнопкой.
Описание, чек-лист, файлы и комментарии пока только читаются из DTO/счётчиков;
редактирование этих полей, выбор проекта, архив/корзина и перенос по пользовательским
столбцам не входят в этот этап. Смена семантического статуса перемещает задачу
в соответствующий базовый столбец по существующим правилам сервера.
Детали показывают последнюю серверную копию, локальный статус виден на карточке.
Полный кэш содержит личные данные аккаунта в SQLite в каталоге приложения;
токен хранится только в системном защищённом хранилище.

## Проверка

В WorkspaceTest добавлены проверки create replay, status replay после новой правки,
конфликта без подтверждения, чужих задач/read-токена, курсора с tombstones и архива.
В Flutter добавлены проверки долговечности тела, потери ответа создания и отсутствия
дубликата при pull, сохранения базовой версии, 409 и принятия сайта, обрыва обхода,
чистых/грязных удалений, read-сессии и разных аккаунтов.

В этой среде нет PHP, Docker и Flutter: backend/Flutter тесты здесь не запускались.
Проверка установщика и ZIP выполнена отдельно. Прогон необходимых тестов выполняется
локально; GitHub Actions повторяет серверные проверки перед выкладкой.

1. Сначала установить патч, выполнить тесты, commit/push и дождаться зелёного Actions.
2. Запустить приложение Linux/Android. Выйти/войти для замены read-токена на write.
3. Создать задачу в экране аккаунта: она должна появиться на сайте один раз.
4. Без интернета создать ещё задачу и сменить статус. Закрыть/открыть приложение:
   записи и очередь должны остаться. Включить интернет, нажать синхронизацию.
5. Изменить серверный статус на сайте, затем синхронизировать чистый клиент.
6. Для конфликта: без сети изменить задачу в приложении; изменить ту же задачу
   на сайте; включить сеть и синхронизировать. Локальная очередь должна остановиться
   на конфликте, сайт не должен перезаписаться. Проверить «Принять сайт».
7. Выйти/войти в тот же аккаунт; проверить сохранение его очереди. При другом аккаунте
   прежние задачи не должны отображаться или отправляться.
