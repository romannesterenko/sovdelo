# Этап 29 — синхронизация без ожидания сети в обычных правках

Задачи, статусы, пункты, комментарии, метки и выбранные копии файлов сохраняются
локально, после чего UI освобождается, а HTTP выполняет отдельный WorkspaceWorker.
Список/деталка и открытые истории подписаны на локальные обновления worker:
подтверждение сервера видно без закрытия экрана и ручного перечитывания.
Схема SQLite v6, API и серверные миграции остаются прежними.

## Последовательная работа

Один worker на открытый аккаунт; несколько запросов на синхронизацию объединяются.
Изменение, пришедшее во время текущего цикла, вызывает следующий проход. Снимки
локальных данных также перечитываются последовательно. Сам сетевой worker НЕ
равен OS background service: после закрытия приложения Dart-процесс может прекратиться.
Очередь остаётся в SQLite и возобновляется при следующем открытии.

В активном приложении Timer проверяет очередь каждые 30 секунд; при отсутствии
локальных изменений серверные данные обновляются примерно раз в минуту. При возврате
из paused/hidden запрашивается проход с учётом задержки ошибок. Inactive от системного
диалога выбора файла отдельно не считается уходом в фон. Пока приложение в фоне,
периодические новые проходы не начинаются; текущий запрос может закончиться.

При сетевой/серверной ошибке — задержка 30/60/120/240/300 секунд. Ручное обновление
может обойти эту сетевую задержку. HTTP429 учитывает Retry-After (число секунд,
в пределах 1–3600, при отсутствии 60); ручная кнопка эту задержку не обходит.
Определителя восстановления сети/нового connectivity-пакета нет: возобновление
происходит по Timer, возврату приложения или ручной кнопке. Поэтому «интернет появился»
не означает немедленную передачу в ту же миллисекунду.

Открытие комментариев/файлов и их кнопки обновления планируют чтение в том же worker.
До HTTP виден кэш. Новые сообщения/метки и копии файлов остаются в очереди до
подтверждения. UUID/замороженные тела запросов и проверки SHA не меняются.
Старая неуспешная попытка не переводит обратно в blocked запись, уже подтверждённую
полным чтением истории. Конфликты API409 по-прежнему требуют решения пользователя.

## Открытый редактор

Редактор вычисляет разницу с исходной локальной записью и сохраняет только изменённые
поля. В SQLite-транзакции проверяется, что именно эти поля не менялись с открытия.
Если сервер обновил другое поле, пользовательское изменение можно сохранить, не
возвращая чужое поле к старому значению. Если изменилось то же поле — DraftConflict:
редактор остаётся открыт, введённый текст не стирается. Можно скопировать нужное и
заново открыть актуальную задачу. Автоперезаписи и кнопки «перезаписать без проверки» нет.
Проверка не заменяет expected_version на сервере: конфликт после начала HTTP всё
равно возвращается в существующий экран сравнения версий.

Статус и чек-лист из деталки также проверяют локальную базовую версию соответствующего
поля. Оптимистичная отметка при отказе откатывается к фактической локальной записи.
Редактор не подписывается на замену своих TextEditingController фоновыми данными:
обновления под ним не затирают набранный текст. Метки, разрешившие локальный UUID
в серверный ID во время редактирования, могут потребовать повторного открытия выбора
при одновременной правке этого набора; конфликт не приводит к молчаливой потере данных.

## Сессия и завершение

На 401 новые сетевые попытки прекращаются, очередь сохраняется. Открытые формы не
закрываются принудительно: можно сохранить их локально/скопировать текст и закрыть.
Когда открытые экраны закончены, аккаунт возвращается к входу с сохранённой очередью.
Новые серверные изменения без повторной авторизации не отправляются.

При выходе worker прекращает брать следующие элементы и ожидает текущий запрос,
после подтверждения закрывает SQLite. Он не досылает всю длинную очередь перед
выходом. На это могут уйти до текущего сетевого таймаута: 25с JSON/до120с файла;
отзыв токена — отдельный запрос. Выход/первый вход, разбор конфликта и явное
«Сохранить как…» со скачиванием по-прежнему могут ждать сеть. Обычный набор текста,
локальное сохранение, открытие кэша и продолжение работы этого ожидания не требуют.
Файловый picker и копирование выбранного облачного файла также завершаются до
появления долговечной локальной очереди. Полного OS upload service/отмены HTTP
в полёте в этом этапе не добавляли.

## Проверки

Подготовлены 7 unit-тестов worker: отсутствие ожидания сети при локальной записи,
один сетевой цикл при множественных request, 429/Retry-After, повтор после офлайн,
foreground/background, 401 и сохранность очереди при закрытии во время запроса.
Дополнительно 3 модельных и 1 widget-тест черновика: конфликт того же поля, сохранение
изменённого поля без возврата другой серверной правки, сохранность текста при отказе и защиту копии файла от устаревшей команды удаления.
Flutter SDK в среде подготовки отсутствует: эти тесты здесь не запускались.
Установщик проверяется отдельно на соответствие патчу28, повтор и ручные изменения.

Приёмка Android/Linux:
1. Отключить интернет, изменить несколько задач, пункты, комментарии: после локальной
   записи управление возвращается, можно перейти к другой задаче без таймаута HTTP.
2. Включить сеть, оставить приложение открытым или нажать обновление: очередь уходит,
   карточки/открытые истории меняют состояние без перезапуска.
3. При запущенной отправке добавить ещё правку: она должна уйти следующим проходом,
   без дубликатов. Повторить после полного закрытия/открытия приложения.
4. Открыть редактор, изменить название/описание на сайте, дождаться обновления worker,
   сохранить то же поле: текст остаётся в форме, появляется сообщение о конфликте.
5. Если на сайте поменялось только описание, сохранение нового названия не должно
   вернуть прежнее описание. Проверить итог на сайте.
6. Отозвать токен, не теряя локальную очередь; повторно войти в тот же аккаунт.
7. На телефоне свернуть/развернуть приложение и проверить продолжение работы.
