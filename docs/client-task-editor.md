# Этап 23 — редактор задачи и проекты офлайн

Редактор в экране аккаунта: название, описание, срок YYYY-MM-DD с календарём/очисткой,
приоритет, проект или «Без проекта». Сохранение записывает только отличающиеся поля
и операцию очереди одной транзакцией. Можно редактировать и ещё не отправленную задачу:
сначала идёт create, затем edit с версией из подтверждения create. Описание, проект
и срок не встраиваются задним числом в уже подготовленное тело создания.
Статусы продолжают отправляться отдельными операциями.

SQLite аккаунта обновляется v1 → v2 в прежнем файле, без удаления данных.
Добавлены description/due_date/priority/project_id, снимок fields в очереди,
локальная таблица account_projects. Существующие подготовленные тела и UUID операций
не меняются. Новые поля старых задач берутся из сохранённого remote_json.
Тестовая база probe.sqlite3 не меняется.

Синхронизация полностью читает задачи, затем активные проекты через существующий
GET /projects (все страницы). Только после успеха обоих чтений заменяется кэш.
Ошибка чтения проектов не затирает прежние задачи/проекты и не очищает очередь.
Проекты доступны без сети после хотя бы одной успешной полной синхронизации.
Архивные/удалённые проекты не предлагаются для нового выбора. Если проект текущей
локальной задачи стал недоступен, редактор показывает его ID как недоступный и
позволяет выбрать другой/без проекта. Сервер повторно проверяет владельца и активность.
Пагинация проектов использует существующий offset API; изменения списка во время
обхода могут отразиться целиком только при следующем обновлении, как и прочий кэш.
Создание/переименование проектов в этом патче не реализуется.

POST /api/v1/sync/operations дополнен:
```json
{
  "operation_uuid": "UUID",
  "kind": "edit",
  "task_id": 123,
  "expected_version": 2,
  "fields": {"title": "Название", "description": "Текст", "due_date": null, "priority": "high", "project_id": null}
}
```
fields: непустой объект только с указанными ключами. title до 240 символов,
description до 20000, due_date YYYY-MM-DD/null, priority normal|high,
project_id свой активный проект/null. Неизвестные поля запрещены. Права write обязательны.
Существующие create/status и их сохранённые подтверждения совместимы.
Порядок полей fields не влияет на fingerprint.

Динамическая проверка существования/активности проекта выполняется внутри транзакции
после проверки подтверждения операции. Поэтому повтор уже успешной операции возвращает
прежний ответ даже если проект потом попал в архив. TaskOrder проверяет проект и
обновляет поля по существующим правилам. Неверная ожидаемая версия — 409 без записи.
Правки description/title не сбрасывают статус, чек-лист, метки, файлы или комментарии.
Очистка nullable-полей передаётся явным null, отсутствие поля означает «не изменять».

Конфликт остаётся конфликтом всей задачи: автоматического объединения полей нет.
Диалог показывает локальные и серверные название, статус, описание, проект, срок и
приоритет. Принятие сайта после подтверждения заменяет все поля задачи и удаляет
её ожидающие правки; остальные задачи не затрагиваются. Изменённая локальная копия
не перезаписывается входящим pull до подтверждения или решения пользователя.

Ограничения: редактирование чек-листа, комментариев/файлов/меток, управление проектами,
архив/корзина и фоновые обновления — следующие задачи. Синхронизация по-прежнему
при открытии, после правки и вручную; после восстановления сети нажать кнопку.
Серверная деталка показывает сохранённую серверную копию, редактор — локальные поля.

## Приёмка

1. Сначала тесты и push, дождаться зелёного Actions с новой версией API.
2. На Linux и Android открыть аккаунт. Обновить список, проверить проекты офлайн.
3. В карточке нажать «Редактировать», изменить все пять полей и сохранить.
4. Проверить на сайте название/описание/срок/приоритет/проект.
5. Отключить интернет, создать задачу и до отправки изменить описание/проект.
   Перезапустить: поля и очередь должны сохраниться. Включить сеть, синхронизировать:
   одна задача с итоговыми полями, очередь пуста.
6. Убрать срок, описание и проект; проверить null на сайте и после перезапуска.
7. Создать конфликт редактора с изменением на сайте. Убедиться, что сайт не перезаписан,
   диалог показывает обе версии и принятие сайта заменяет локальные поля.
8. Проверить, что старые неподтверждённые операции патча 22 сохранились после миграции.

Добавлены 3 Laravel-проверки контракта/повтора/проекта/конфликта и 6 Flutter-проверок
сохранения, редактирования до create-ack, pull, null/неизменённых полей, отката и
миграции v1 с подготовленной операцией. PHP/Flutter SDK в среде подготовки отсутствуют:
эти тесты нужно выполнить локально. Проверка установщика выполняется отдельно.
